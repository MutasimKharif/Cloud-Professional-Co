A step-by-step cloud migration checklist

Eight stages from “why are we moving?” to switching off the old servers — the checklist we use to keep migrations predictable.

By the CloudPros team14 November 20268 min read

Most migrations that go wrong don’t fail on the technology. They fail because nobody agreed why the move was happening, a dependency was discovered on cut-over night, or the old servers kept running — and costing money — long after the new ones went live. This is the checklist we work through, in order.

1. Agree why you’re moving

  • Write down the reasons: hardware reaching end of life, a data center contract ending, resilience, speed of delivery, cost.
  • Turn each into something you can measure — monthly run cost, recovery time, release frequency — and record today’s number.
  • Name an executive owner who can make decisions when trade-offs appear.

2. Build an inventory with dependencies

  • List every application, server, database, file share and scheduled job, with an owner for each.
  • Map what talks to what. Network flow data and discovery tools help, but interview application owners too — they know about the monthly batch job that no tool will find.
  • Note licensing: some software licenses can’t move to the cloud as-is, or cost more there.

3. Classify data and decide where it may live

Before designing anything, decide which data is personal, sensitive or regulated, and where it is allowed to be stored. In Saudi Arabia that means checking the PDPL for personal data, the NCA’s Cloud Cybersecurity Controls, and your sector regulator’s rules — SAMA’s, for example. AWS has announced its first Region in the Kingdom for launch by December 2026; if you plan to use it, confirm that the services you need are available there.

4. Choose a strategy for each application

AWS describes seven options, often called the 7 Rs. Decide one per application and write down why:

  • Retire — switch it off; nobody needs it.
  • Retain — keep it where it is, for now or for good.
  • Rehost — move the server as it is (“lift and shift”).
  • Relocate — move a whole platform, such as VMware workloads, without changing it.
  • Repurchase — replace it with a SaaS product.
  • Replatform — small changes for a better fit, such as moving a database to Amazon RDS.
  • Refactor — redesign it to use cloud services fully.

Rehosting first and improving later is often the fastest way out of a data center. Refactoring pays off for the applications that change often or need to scale.

5. Build the landing zone first

The landing zone is the foundation every workload lands on. Have it in place before anything moves:

  • Separate AWS accounts for production, non-production, security and shared services, managed with AWS Organizations or AWS Control Tower.
  • Single sign-on through IAM Identity Center, connected to your directory.
  • Central, tamper-resistant logging with an organization-wide CloudTrail trail.
  • An IP addressing plan that doesn’t overlap your offices, plus the VPN or Direct Connect link back to them.
  • Guardrails such as service control policies, and GuardDuty and Security Hub switched on everywhere.
  • Backups and budgets configured from day one.

6. Plan waves and rehearse

  • Group applications that depend on each other into the same wave. Start with something low-risk to prove the process.
  • Use AWS Application Migration Service for servers, AWS Database Migration Service for databases and AWS DataSync for file data, so data replicates ahead of time.
  • Test each application in AWS before cut-over: functions, integrations, performance and security.
  • Agree a change freeze for the systems in the wave.

7. Cut over with a way back

  • Lower DNS time-to-live values a few days before, so the switch takes effect quickly.
  • Run a final sync, switch traffic, and smoke-test the critical paths.
  • Hold a go/no-go check against criteria agreed in advance — and a rollback plan you have actually tested.
  • Keep the old system available, read-only, until the agreed rollback window has passed.

8. Finish the job

  • Decommission the old servers and cancel their licenses and support contracts. This is where much of the expected saving comes from.
  • Right-size instances once you have a few weeks of real usage, then consider Savings Plans for the steady part.
  • Set AWS Budgets alerts, update runbooks and disaster-recovery plans, and compare your measures with step 1.

A migration run this way is rarely exciting — which is the point. Each stage produces something you can review before the next one starts, so surprises show up on paper rather than in production.

Key takeaways

  • Write down why you’re moving and how you’ll measure it.
  • Map dependencies before choosing a strategy for each application.
  • Decide where data may live before you design anything.
  • Build the landing zone before the first workload moves.
  • Move in waves, starting with low-risk applications.
  • Every cut-over needs a go/no-go check and a tested rollback.
  • Switch off what you’ve replaced, then right-size.
