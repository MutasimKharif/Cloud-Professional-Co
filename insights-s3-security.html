Securing your S3 buckets: a practical guide

Most S3 data exposures come from configuration, not from S3 itself. Seven settings and checks that keep your buckets private — and prove it.

By the CloudPros team14 November 20267 min read

Amazon S3 is one of the most reliable services AWS runs, yet “exposed S3 bucket” keeps appearing in breach reports. The reason is almost always configuration: a bucket made public for a quick test, an old access control list nobody remembers, or a policy that grants far more than it needs to.

Since 2023, new buckets are safer by default — Block Public Access is on, access control lists (ACLs) are disabled, and new objects are encrypted with S3-managed keys. But buckets created before then keep their old settings, and every default can be switched off. Here is what we check on every AWS account we work on.

1. Block public access for the whole account

Block Public Access can be set per bucket, but the account-level setting overrides all of them and stops anyone from making a bucket public by mistake. Turn on all four options:

aws s3control put-public-access-block \
  --account-id 111122223333 \
  --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

If you use AWS Organizations, apply it to every account and add a service control policy that prevents it being turned off. Need to serve a public website from S3? Put Amazon CloudFront in front with Origin Access Control, so the bucket stays private and only CloudFront can read it.

2. Turn off ACLs

ACLs are an older permission system that sits alongside bucket policies and is easy to overlook. Set Object Ownership to Bucket owner enforced: ACLs stop having any effect, and access is decided only by policies you can read and review in one place.

3. Grant the least access that works

  • Give each application its own IAM role with access to the specific bucket and prefix it needs — not s3:* on *.
  • Avoid "Principal": "*" in bucket policies unless it is tightly restricted by conditions, such as a specific VPC endpoint with aws:SourceVpce.
  • To share a file temporarily, use a presigned URL that expires, rather than opening the bucket.
  • Run IAM Access Analyzer: it lists every bucket that is shared publicly or with another AWS account, so you can confirm each one is intended.

4. Require encryption in transit

Add a statement to every bucket policy that denies requests not made over TLS:

{
  "Sid": "DenyInsecureTransport",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::example-bucket",
    "arn:aws:s3:::example-bucket/*"
  ],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}

5. Choose the right encryption at rest

S3-managed encryption (SSE-S3) is on by default and is fine for much data. Use SSE-KMS with a customer managed key when you need to decide who can decrypt the data, separately from who can read the bucket, and to see every use of the key in AWS CloudTrail. Enable S3 Bucket Keys with it to cut the number of KMS requests — and their cost.

6. Protect against deletion and ransomware

  • Turn on versioning, so overwritten or deleted objects can be recovered, and add lifecycle rules so old versions don’t grow forever.
  • For backups, records and anything you must keep, use Object Lock in compliance mode: nobody — including administrators — can delete or change the data until the retention period ends.
  • Replicate critical data to a bucket in a separate account. If the data must stay in Saudi Arabia, check where the copy lands before you switch replication on.

7. Log and watch

Settings drift. Someone will eventually change a policy, so make sure you would notice:

  • CloudTrail data events for sensitive buckets record who read or changed which object.
  • Amazon GuardDuty S3 Protection flags unusual access, such as reads from known malicious addresses or sudden mass downloads.
  • Amazon Macie finds personal and sensitive data in your buckets — useful when the PDPL requires you to know where personal data lives.
  • AWS Config rules such as s3-bucket-public-read-prohibited and s3-bucket-ssl-requests-only report any bucket that drifts from your baseline.

Where to start

If you only do two things this week, turn on account-level Block Public Access and run IAM Access Analyzer. Together they close the most common exposure and show you everything that is shared today. The rest can follow as a short project — and is exactly the kind of evidence auditors ask for under the NCA’s cloud controls.

Key takeaways

  • Block public access for the whole account, not bucket by bucket.
  • Disable ACLs and control access with policies only.
  • Deny any request that doesn’t use TLS.
  • Use KMS keys when you need to control and audit who can decrypt.
  • Turn on versioning, and Object Lock for data you must not lose.
  • Log object access and let GuardDuty, Macie and Config watch for you.
